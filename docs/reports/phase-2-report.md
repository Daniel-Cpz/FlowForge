## Summary

POST commits canonical Job + durable dispatch intent in one PostgreSQL
transaction. A bounded dispatcher publishes minimal Redis Streams messages;
one serial worker reloads authoritative data, atomically claims a Job and one
attempt, executes a context-aware SLEEP, commits terminal Job + attempt, and
ACKs delivery. Publication may repeat. Delivery is at-least-once, with explicit
post-claim crash limitations; no exactly-once guarantee is made.

## Implemented

- Append-only migration 000003 with forward/down and existing-QUEUED backfill.
- Atomic Job/outbox creation, canonical readback and Phase 1 HTTP error contracts.
- Bounded pending scan (100), one-second dispatch cycles and 30-second
  still-QUEUED republication; no database transaction spans Redis or SLEEP.
- Redis Streams consumer group at 0, COUNT 1 / BLOCK 500 ms, explicit XACK,
  version 1 + canonical UUID messages without Job payload.
- Single serial executor plus dispatcher goroutine; atomic conditional claim,
  transactional attempt creation and owner/attempt-guarded terminal persistence.
- SLEEP exact duration_ms integer contract, 0..10000 ms inclusive. Unsupported
  type/invalid payload asynchronously becomes FAILED with static result codes.
- Context-aware shutdown with FAILED/execution_cancelled bounded cleanup.
- Sanitized event logs, bounded dependency retries and no premature ACK on DB errors.
- Redis AOF everysec, named volume, noeviction and configurable stream namespace.
- Real PostgreSQL/Redis integration and process smoke; CI now provisions Redis
  alongside PostgreSQL so queue tests have a real service.

## Not Implemented

RUNNING crash recovery, business retries/backoff/jitter, submission idempotency,

## Failure / Edge Case Validation

Job insert failure commits neither record. Intent insertion failure rolls back
the Job. Redis connection failure preserves queued Job and null marker. A new
dispatcher recovers pending intent. Redis publication followed by a real marker
constraint failure produces duplicates but only one business attempt/execution.
Deleting only a disposable stream demonstrates reconstruction of still-QUEUED
work after the publication eligibility interval.

Atomic claim failure rolls back Job + attempt and does not ACK. Terminal update
failure rolls back both records and leaves RUNNING + pending. Terminal and
RUNNING duplicates do not execute. Poison/missing messages do not crash the
worker. Context cancellation interrupts the timer; detached bounded cleanup
persists FAILED if storage remains available. Static result errors and event
codes keep credentials, payloads and raw DB errors out of API/runtime logs.

## Known Limitations

- Abrupt crash or ambiguous database response after claim may leave RUNNING
  indefinitely. No heartbeat, leases, stale-owner fencing or recovery exists.
- Finalize failure stops the worker without ACK; terminal commit + ACK failure
  retains terminal data and possibly pending delivery. No automatic restart
  policy or stale pending-consumer reclaim is installed.
- Delivery relies on continued dispatcher operation and eventual dependency
  availability. Redis AOF everysec can lose recent writes; QUEUED reconciliation
  covers notification loss but never recovers RUNNING execution.
- Stream entries, old consumer metadata and outbox history grow without cleanup.
- Existing QUEUED Jobs are backfilled and processed on Phase 2 startup;
  unsupported legacy types fail deterministically. Create still accepts those
  types/payloads for Phase 1 contract compatibility.
- Idempotency keys, priority, max-attempt metadata and general timeout are not
  submission deduplication, scheduling, retry or timeout policies.
- Only one process / one active Job is supported operationally. No performance,
  exactly-once, external-side-effect or production-readiness claim is made.
