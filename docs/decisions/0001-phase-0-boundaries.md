# 0001 — Phase 0 boundaries

Status: Accepted

## Context

FlowForge needs an explainable, testable foundation before distributed execution.
Most current work is configuration, lifecycle and durable job persistence.

## Decision

Use a Go modular monolith with separate API and worker entrypoints. Standard
net/http provides the small routing surface. Domain owns repository contracts;
pgx implements persistence. PostgreSQL owns durable state. Redis is connected
but carries no jobs. UUIDs are generated by the application. Use simple embedded
SQL migrations with version tracking, transaction locking and rollback files.
Only actual create/get/list use cases receive interfaces and implementations.

## Consequences

One codebase keeps changes and tests local while separating process lifecycle.
The worker consumes a database connection budget even without executing jobs;
this is intentionally limited to infrastructure verification. Migration files
must remain immutable once applied; checksum/drift verification is not provided.
No worker repository, empty worker service or future scheduling stub is created.
State graph validation is not a distributed transaction or fencing guarantee.

## Alternatives

Microservices, gRPC and a large framework add operational surface without a
current need. Redis-only persistence risks losing durable job truth. A mature
migration CLI is a reasonable later replacement; two SQL versions currently
need only a small auditable runner. Frontend and observability platforms wait
for real execution behavior to observe.
